## 2. ★ 这一轮学到的硬事实（都带证据，别再重推）

### 2.1 「禁止回弹」为什么必须删（已验）

听歌页的**下拉关闭是经过那条列表接管的**：列表在顶部时把下拉让给窗口。
钉住之后列表**没有任何内部可滚范围**（`content.h == bounds.h`）⇒
`alwaysBounceVertical = true` 时拖动只能落到"让位"那条路 ⇒ 关得掉；
写成 `false` 就**既不滚也不让位** ⇒ 窗口永远收不到那次下拉 ⇒ **播放器划不掉**。

* 日志 41（全量 37 份里唯一 `bounce=off`）：`[OneScreen] 已关掉列表的回弹（alwaysBounceVertical=false）`；
* 日志 43（修完）：`bounce=on` + 用户实测能退出。
* **pw 也从没碰过它**：它只改 `contentInset.bottom`，并在 `PlayerField.x` 给背景场**向上多铺 200pt**，
  注释写着那是"the pull that dismisses the player"。

⇒ **纪律：在听歌页上，`alwaysBounceVertical` 与"滚动"都别碰；要一屏不滚就只改 inset。**

### 2.2 定向转储（`[NPVTree]`）——以后取证的默认手段

`ViewTreeDumper.setPage(_:)` 由**页面自己的 hook** 登记页根（听歌页 =
`NPVScrollViewControllerHook`），在登记过的页上：
**只走这一页子树、预算 1200、tag 用 `[NPVTree]`**；其它屏照旧 `[Tree]`（整窗 400 节点）。
**为什么必须**：听歌页一棵树约 **800 节点**，整窗 BFS 的 400 预算永远够不到底部那一坨
—— 日志 40/41 的 20 份树**每份正好 402 行**就是这个原因。

### 2.3 pw 的播放页结构（读源码得来，GPL-3.0 那侧）

`Player.h` 是总纲，原话：*"Spotify's full screen player **kept** … Every control stays Spotify's own …
**one screen with nothing under it**: every card is collapsed and the player does not scroll.
**The lyrics come to the player itself, the way the Music app shows them, when the lyrics glyph is
tapped.**"*

### 2.5 歌词的三个真 bug（日志 45 判读，已修未验）

1. **选歌只比时长**（±5s + 取第一个）⇒ 翻唱/伴奏/同曲异名会被选中 ⇒ 用户"歌词全是错的"。
   **旧日志（readlog 10/11/18）证明这从最初就是这样**，不是新引入的；只是换成 NetEase 单源后暴露。
   → 现在要求**歌手 + 时长都对得上**（歌手名来自 metadata 的 `artist_name` / `artist_name:1`…）。
2. **`<Music>` 被当正文**：网易用尖括号占位标间奏，而既有 9 条"标注行"规则只认 `[方括号]`/`♪`。
   → `LyricsMarkerFilter` 新增**尖括号占位行**，网易两条建行路径都过滤（**丢整行**，不留空行）。
3. **"只画逐词"门禁太严**：Spotify 自己的卡片**行级也渲染**，而那张卡正是被「一屏」折掉的
   ⇒ 没逐词的歌**两边都空**。→ 放宽到行级（`hasUsableWordLevelData || hasUsableLineLevelData`）。

## 4. ★ 本机环境的纪律（这一轮又踩了两次，务必照做）

1. **五条自检不做类型检查**（`orion_hook_guard` / `swift_brace_check` / `swift_member_check` /
   `l10n_lint en` / `l10n_lint zh-CN`）。它们能抓"缺 import Orion"这类，**抓不到**下面两类：
   * **逐成员初始化器是位置敏感的**：给 SwiftUI 视图加字段后，参数顺序**必须与属性声明顺序一致**。
     CI 原话：*"argument labels do not match; expected …previewHeaderInset:onSeek:…trackArtist:
     transparentBackdrop:clock:…"* —— 加字段后**去读一遍结构体属性顺序再写调用点**。
   * **`@MainActor` 类型不能在非隔离上下文里被调**：门面/宿主标了 `@MainActor`，
     调用点就得在 MainActor 上；**Orion 的 hook 方法不能加 `@MainActor`**
     （代码生成器会拼出 `@MainActoroverride`）⇒ 用
     `onMainThreadSync { … }`（[`LyricsChromeVisibility.swift:25`]）。
     **提交前把新 API 的所有调用点列出来逐个看。**
   * 附带：逐成员初始化器失败后，**紧邻几行会跟着报"推断不出类型"**（如 `= .clear`）——
     那是恢复状态，**先修第一条**。
2. **查历史证据要同时看两个目录**：`C:\dsh\ipa\`（09-30 之后，`eeveespotify_debug_shared N.log`）
   与 **`C:\dsh\readlog\`**（09-26/27，`eeveespotify_debug N.log`）。这一轮又栽了一次
   （只翻 `ipa` ⇒ 差点得出"以前没这问题"的错误结论）。
3. `pwsh` 必须带 `sandbox_permissions: "danger-full-access"`（否则 `0xC0000142`）；
   控制台 GBK ⇒ 中文输出**写进 UTF-8 文件再 read**；PowerShell 里**别在双引号字符串里放中文双引号**
   （`"…"…"` 会把解析器搞崩，用 `「」`）。
4. 删/改**别人的视图**时：只改**透明度**或**加自己的子视图**；**不 hidden、不移除**（Encore 布局会因 hidden 重排）；
   记好还原表；几何一律 `transform`（**不动约束** —— stack view 会把约束写回）。
5. 递归走别人的子树要**有界**（`maxNodes`），并且**别碰非图形的叶子**。

## 9.2 ★★ 闪烁的机制：**逐层去"按回去"天生慢一拍** ⇒ 改成"整颗按钮钉住"

日志 49 在 **02:59:31–02:59:38** 这一段只有这一种行在不断重复（**约 4 次/秒、持续 7 秒**）：

```
[NPVControls] … 本拍把 1 处原生内容按回透明（按钮的动作/状态/无障碍保留）
[NPVControls] … 本拍把 0 处原生内容按回透明（按钮的动作/状态/无障碍保留）
[NPVControls] … 本拍把 1 处原生内容按回透明（按钮的动作/状态/无障碍保留）
…（1/0/1/0 交替 20+ 次）
```

⚠️ **2026-10-05 用户澄清**：**这 7 秒他一直在快速按暂停键**。

⇒ 我先前那条推论（"用户什么都没做 ⇒ 稳态拉锯 ⇒ Spotify 每 0.25s 写回一次"）**作废**。
正确的读法简单得多：**每按一次，就多出一层新图形**（pw：*"The holder Spotify crossfades a snapshot
of the disc in when play turns to pause."*）——

* `1` = 这一拍新出现了一个要处理的（那一次的圆盘快照）；
* `0` = 这一拍没有。

**所以病根是"它出生到我们钉住之间那一帧"，不是"按回去不够快"。**
逐叶子 / 逐圆盘地去追，**每一版都注定慢一拍**，因为新图形不是同一批实例。

### 修法（结构性，不再追）

| # | 做法 | 为什么 |
|---|---|---|
| ① | **把 `SPTNowPlayingPlayButton` / `Previous` / `Next` 三颗按钮整个 layer 钉住** | 之后 Spotify 往它们里面塞多少新图形（圆盘 / 原生字形 / 每按一次新建的快照 / 缓冲 spinner）**出生即不可见** ⇒ 那一帧的窗口从根上关掉，不需要再"追" |
| ② | 钉**只动 layer、不写 `alpha`** | 渲染看**呈现层**（被钉在 0 ⇒ 看不见）；命中判定看**模型值** `alpha`（一点没变 ⇒ 按钮照样收得到触摸）。这是播放/暂停还活着的前提（`PlayButtonView.uiButtonTapped` 是由按钮内部那颗 `CondensedButton` 发出去的） |
| ③ | 字形搬到**按钮的兄弟层**（`button.superview`），每拍按按钮的框重算 | 字形若还是按钮的子视图会**跟着被钉没**。pw 把字形放进按钮内部是为了跟"按下回弹"，而按钮整层钉住后那份回弹本就看不见 ⇒ 搬出来不损失任何可见的东西 |
| ④ | 新钉住一颗按钮后补一串**位置复核**（0.05/0.15/0.35/0.6s） | 只为让字形跟上按钮前几拍还没稳定的坐标；**不再是**"把 alpha 按回去" |

**还原**：撤钉（`removeAnimation`）+ 拿走字形。**原生一个字节都没改过**。

> **为什么不用 pw 那套**（`Kit/SGRRestyle.m` 的 `SGRSuppress`：把实例换成运行时子类、覆写 `setAlpha:`）：
> ① 纯公开 API（`CABasicAnimation`），本机没有编译器，能少一处类型陷阱就少一处；
> ② ★ 它的 `subclassable()` 是 `strncmp(name,"_Tt",3) != 0 && !strchr(name,'.')`，而我们的
> `MixedPlayButtonDecorationView` 真名是 `_TtC28EncoreConsumerMobile_BaseKit29…`（**`_Tt` 开头**）
> ⇒ 照抄只会得到它自己那句 `cannot keep being suppressed, set once per call`；
> ③ 覆写 `setAlpha:` 会**连带改掉命中判定**（我们最不想要的副作用）。

# 10. 「一屏开着还能像橡皮筋一样往下滑」—— **pw 没解决，它是刻意保留的**（2026-10-05 追问）

> 用户原话：*「但是还有个问题是在开启不可往下划（名字叫什么忘了）的时候，还是能和橡皮筋一样往下滑。

## 10.1 直接把 pw 的原文摆出来

`spotipw-v0.21.1/tweak/Sources/Redesigned/Player/PlayerScroll.x` 文件头（GPL-3.0 隔离副本）：

> *"The list is not switched off: the pull that dismisses the player rides on its own pan recogniser. …
> **Turning scrolling off takes that recogniser out with it and the player can no longer be swiped away.**
>
> So the range is closed instead: the bottom inset is set to whatever makes the furthest the list can
> scroll its own top. **A drag upward then only stretches and springs back**, a drag downward still
> carries the offset below zero, and the dismissal is untouched."*

逐句对到我们这边：

| pw 的话 | 含义 |
|---|---|
| *"the range is closed instead"* | **我们做的正是这一件事**（`inset.bottom → min(want, 0)`） |
| *"**A drag upward then only stretches and springs back**"* | ★ **pw 明确承认那条橡皮筋还在** —— 它没消除它 |
| *"a drag downward still carries the offset below zero, and the dismissal is untouched"* | ★ 与上一句是**同一件事的两面**：**那个负的 `contentOffset` 就是下拉关闭的输入** ⇒ 去掉回弹 = 去掉负偏移 = **关闭手势没有输入** |

## 10.2 我们的日志证明「范围」那一半是对的

日志 49（用户这次报的现场）：

```
[OneScreen] 把列表自带的 inset.bottom=34pt 归零（内容刚好一屏时，那正是还能往下滑的距离）
[OneScreen] diag inset.bottom=0 content.h=896 bounds.h=896 adj.top=0 adj.bottom=0 bounce=on panRecs=3
[OneScreen] collapsed card root …（共 5 种）
```

★ **`content.h == bounds.h`（896 == 896）⇒ 一点可滚范围都不剩了**。
用户感到的那点位移**纯粹是回弹**，不是"还有内容能滚上去"。**「一屏」这一半是做对的。**

## 10.3 而"去掉回弹"这一招我们**真机上已经试过、并且判死了**

日志 41（全量 37 份里**唯一**一份 `bounce=off`）就是那次实验：把 `alwaysBounceVertical` 关掉，
结果**播放器再也划不掉**，开关当天整块删除（`SESSION_2026-10-03_NIGHT.md` §9）。
pw 也写明连滚动都不能关（上面那句 *"Turning scrolling off takes that recogniser out with it"*）。

⇒ 结论：**"拉不动"与"还能划掉"目前是同一个手势的两种用法，不能只要一个。**

## 10.4 唯一的出路与它的两个障碍

**出路**：**自己接管下拉关闭**（把列表在顶部的下拉读成"关闭进度"，自己驱动 dismiss），
拿到之后才敢关 `bounces`。两个已知障碍：

1. pw 的挂点（`SPTBarInteractivePresentationController` / `SPTBarOverlayPresentationTransition`）
   在 **9.1.88 上不存在**（探针实测缺这 2 个）⇒ **没有现成可抄的挂点**；
2. 本仓库在"自己加手势"上有前车之鉴（双击手势整块删掉，见 §10 之外的 `SESSION_2026-10-03_NIGHT.md` §10）。

**三档选择**（已写进 `NowPlayingOneScreen` 文件头，**等用户拍板，不擅自做**）：

| 档 | 做法 | 代价 |
|---|---|---|
| **A** | **接受它**（pw 同款） | 0；只需在设置页文案里说清"下拉那一下就是关闭手势本身" |
| **B** | **自己接管关闭手势**（独立一轮） | 中高：要 hook 列表的 pan、自己做关闭驱动；成了才能关 `bounces` |
| **C** | 只关一端 | ❌ **不存在**：`UIScrollView` 没有"只关顶部回弹"的公开开关（`bounces` 是两端总闸） |

## 10.5 本轮顺带加的一条**只读取证**（为 B 档铺路，零风险）

`[OneScreen] diag` 那一行补了两格（都是只读，不改任何行为）：

```
bounces=on          ← UIScrollView.bounces（两端回弹的总闸；用户感到的就是它）
pan=<delegate 类名>  ← 列表第一个 pan 的 delegate 是谁
```

**为什么要问 `pan=` 这一格**：pw 说窗口那侧会把自己的 dismiss recogniser 设成
**"等列表的 pan 失败"**。如果哪天我们要让列表在顶部**主动让位**（`gestureRecognizerShouldBegin`
返回 false ⇒ 列表不吃这次下拉、不给回弹，而 dismiss 立刻拿到资格），
那**必须先知道那个 pan 的 delegate 现在是谁**（是不是 nil、是不是 scroll view 自己、
能不能接管而不破坏别人）。**一次只读的取证，省一轮瞎猜。**

⚠️ 顺带：模块注释里那句"我们和 pw 的两处不同"（重算时机 / 代价）仍然成立；
`bounce=on` 仍然是**只读回归哨兵**，`bounce=off` 再出现就说明有人又碰了关闭链条。

# 11. 「点歌词，封面往左上变小跑」这个动画怎么做 —— 照 pw 重写（2026-10-05）

> 用户问：*「如果点击 歌词 封面会往左上方变小跑的话，动画怎么做」*。

## 11.1 上一版为什么是错的形状：它在动 `frame`

上一版 `ensureCover` 是 `UIView.animate { cover.frame = target }`。两条硬伤：

1. **`layoutAndMount` 每 0.3s 会重跑一次**（`DeclutterChrome` 的复查节拍）—— 每次都要重写封面布局，
   而动画画在 `frame` 上时那一拍就会**打断 / 拽回**它；
2. 本仓库纪律：**`frame` 在 `transform` 非恒等时不可信**。

（顺带：上一版**一次都没跑起来** —— 照片 51 那次是因为 `ensureCover` 挑错了封面对象，
见 §9.4。形状和取值是两个独立的毛病。）

## 11.2 pw 的配方（`PlayerLyrics.x` + `Kit/SGRTokens.m`，GPL-3.0）

| 环节 | pw 的做法 | 出处 |
|---|---|---|
| **布局** | 容器**永远**按"Spotify 封面那个大小与位置"布局，用 **`bounds` + `center`**（不是 `frame`）。原话：*"laid out **at the size and place Spotify draws its cover at** and moved by its transform alone, so a pass that runs while it is up **leaves it exactly where the eye has it** … **Bounds and a centre, not a frame**"* | `PlayerLyrics.x` `place()` |
| **位移** | **只写在 `transform` 上**：`CGAffineTransformConcat(Scale, Move)` = **先缩放、后平移**，关于自己的中心；平移量 `round()` 取整 | `thumbTransform()` |
| **圆角** | ★ **缩放会把圆角一起缩放** ⇒ 想让缩略图"看起来"是 8pt，模型值要写 **8 / scale**。原话：*"a radius under a scale is drawn scaled, so the thumbnail asks for the radius it wants **divided by the shrink**"*；两端是 `SGRRadiusArtwork = 12`（全尺寸）与 `SGRRadiusCover = 8`（缩略图画出来的） | `thumbRadius()` / `SGRTokens.m` |
| **阴影** | 挂在**容器**上（容器不裁剪）⇒ *"the **shadow and the corners travel with it** that way, **instead of a shadow redrawn on every frame**"* | `place()` 注释 |
| **动画** | `SGRMotionLayout` = `0.45s + usingSpringWithDamping **1** + velocity 0`（**临界阻尼、不回弹**），options = `AllowUserInteraction \| **BeginFromCurrentState**` | `SGRTokens.m:96` |
| **无障碍** | **Reduce Motion 打开时整段不做动画**（`performWithoutAnimation`） | `SGRTokens.m:88` |
| **换图那一刻** | *"Spotify's cover goes **the moment** the redesign's own takes its place"* —— 早一步露空档、晚一步两张同屏（一大一小） | `setOpen` 注释 |
| **拿不到图** | *"**the cover stays and the lyrics wait**"* ⇒ **不展开**（我们 `layoutAndMount` 返回 false 就是这条，与 §9.4 独立收敛到同一个取舍） | `setOpen` 注释 |

★ **`BeginFromCurrentState` 是"连点两次不跳"的关键** —— 从当前**呈现位置**接着走，
而不是从模型值重新开始（那种会"啪"地跳回去）。

## 11.3 落地（`NowPlayingLyricsPlate`，本轮）

* 封面拆成 **容器 + 里面 imageView**：容器承载 `transform` 与阴影（不裁剪），imageView 承载圆角与裁剪；
* `ensureCover` 每拍只做"**按 full cover 的 `bounds`/`center` 布局 + 塞图 + 同一瞬间隐去 Spotify 那条**"，
  **不碰动画**；
* 新增 `applyCoverState(open:geometry:completion:)`：算出目标 `transform` 与"除过 scale 的圆角"，
  用 pw 那套弹簧动过去；**Reduce Motion 时不做动画**；
* **收起的收尾挂在 completion 上**（撤我们那张 + 把 Spotify 那条写回），并带令牌 `coverGeneration`：
  动画没走完又被点开时这一次收尾作废；
  ⚠️ `completion` 在"已经在对的位置"与"Reduce Motion"两条路上**也必须被调用**，否则封面撤不掉；
* **切开关 / 页面消失 = 不动画**（`animated: false`）—— 拖着 0.45s 才写回 Spotify 的封面，
  会在转场里露一个"没有封面"的帧；**用户自己点收起 = 动画**。

## 11.4 本轮**没做**的（说清楚）

`LyricsArtworkResolver`（它已经把 `spotify:image:<hex>` → `https://i.scdn.co/image/<hex>`
这条链走通了），但那是**异步**的，要塞进一个同步返回 `Bool` 的 `layoutAndMount` 得先改结构。

## 12.2 「转储 customize 响应体还有用吗」—— ★ **有用，而且是现在唯一的手段**

先把链路摆清（这条链以前被误读成"空转"）：

| 环节 | 落点 |
|---|---|
| 开关 | 设置 → EeveeSpotify 根页「转储 customize 响应体」（`dump_customize_body`） |
| 抓取 | `SpotifyResponsePatcher.dumpCustomizeBodyIfEnabled` —— 在 `patch()` 的 `isCustomize` 分支里、**任何改写之前**抓，所以是**服务端原样那一份**；`didDumpCustomizeBody` ⇒ **每次启动只抓一次** |
| 输出 | 日志里 `[CustomizeBody] base64-begin … base64-end`（整份 `CustomizeMessage`） |
| 转换 | `Tools/eevee-hookfinder/bnk_from_customize_dump.py` —— 剥 `CustomizeMessage → UcsResponse → ResolveResponse → ResolveConfiguration`，产出 `.bnk` |
| **消费方（生产路径）** | `SpotifyResponsePatcher.seedCustomizeDataIfNeeded`（启动时，`Tweak.x.swift:365`）把随包的 `resolveconfiguration*.bnk` 喂成 `cachedCustomizeData` —— **专治"冷启动第一个 customize 是 304、没有 body ⇒ flag 通道整段不执行"**（就是 §10.9 那个"Flag 覆盖空转"的病根）。种子在落袋前会先过一遍 flag 改写，否则 304 回放路径不跑 `patch()`，`[Flags]` 会是 0 行。 |

**★ 关键实测：种子是活的，而且现在跑的就是它。** 日志 48 与日志 49 **每次启动**都是：

```
[CustomizeSeed] 种子就绪 resolveconfiguration_9_1_76.bnk — 1089 条 flag（随包快照，非服务端当前下发）。
                下面那批 [Flags] 行就是**从这份种子**跑改写时打出来的。
[Flags] lyrics flag — scope=ios-feature-lyrics name=enable_lyrics bool=true
…（下面一整批）
```

⇒ 两条结论：
1. §10.9 的"**Flag 覆盖在这台机器上是空转的**"**已经过时** —— 那是**加种子之前**的结论；
   种子（2026-10-01）把它修掉了，现在 `[Flags]` 每次启动都在打；
2. ★ **但随包的那份种子是 9.1.76 时代的 1089 条 flag**。`BundledConfigurationPolicy` 对
   **≥ 9.1.76 一律**返回 `resolveconfiguration_9_1_76.bnk`，而当前基线是 **9.1.88** ——
   也就是说这台机器上跑的是**落后两个小版本**的配置快照。

**所以这个功能不是"还有没有用"，而是"该用它刷一次种子了"**。刷法：
打开那个开关 → 重启 Spotify（**必须是那次启动真的拿到了 customize 的 body**，不是 304）
→ 日志里取 base64 → `bnk_from_customize_dump.py` 转 `.bnk` → 按版本策略接进包里
（要么替换 `resolveconfiguration_9_1_76.bnk`，要么加成 `resolveconfiguration_9_1_88.bnk`
再让 `BundledConfigurationPolicy` 认它）。

⚠️ 前提与已知代价：
* **常态是 304**（日志里 `[HCUS] Missing buffered body for …/v1/customize` 就是这么写的）
  ⇒ 打开开关可能**一整次启动都没有输出**。要拿到 body 得让那一次真的走网络
  （清 App 缓存 / 换网络 / 服务端重下发）；
* 它是**只抓一次**的（`didDumpCustomizeBody`），所以抓到就是抓到，没抓到就等下一次启动；
* ⚠️ **要转 `.bnk` 必须用本地那份日志**：`[CustomizeBody]` 的 base64 与 `[CASITA][HEX]`
  那类"响应体字节"在**分享版**日志里会被 `DebugLogSanitizer` 整段打掉（第 10 步），
  拿脱敏版去跑脚本只会得到一堆 `<hex-redacted>`。

编译器一次报三处：

```
expected ',' separator            （第 387 行 60 列）
cannot find '藏起原生封面' in scope
extra argument in call
```

**病根**：想用引号做强调，写的是 **ASCII 双引号** ⇒ 第一个 `"` 就把字面量关掉了，
`藏起原生封面` 被当成标识符，后面那个 `"…"` 又成了一个多出来的参数。
（仓库纪律里其实早写着这条 —— `SESSION_HANDOFF.md` §4.3：「PowerShell 里别在双引号字符串里放中文双引号」，
同一条形状；我在 Swift 里又踩了一遍。）

## 13.2 全仓扫了一遍：**唯一的实例就是它**

写了个一次性扫描器（状态机：字符串 / 插值 `\(…)` / 原始字符串 `#"…"#` / 行注释 / 多行字符串），
判据是「**字面量闭合引号后面跟了非法字符**」。**先拿用户报的原始那一行做自检**
（扫描器必须抓到它），然后扫我们自己的 275 个文件 / 45585 行：

```
SELF-TEST on the reported line: 1 hit(s)  OK
suspect = 0    （剩下 2 条是合法多行字符串 `"""`，已按行跳过）
```

⇒ **其余一处都没有。** 这类错在仓库里就这一个。

## 13.3 ★ 把它变成第 6 条本机自检：`Tools/eevee-hookfinder/swift_string_check.py`

为什么原来抓不到：`swift_brace_check.py` **只数引号配平**，而这一行有 4 个 ASCII 引号
—— **偶数 ⇒ 放行**。所以必须有下一条。

```

OK：275 个文件 / 45585 行：字面量闭合引号全部合法      （干净仓库 exit 0）
```

**两向验证过**（仓库纪律：检查器必须两向验证）：

| 输入 | 结果 |
|---|---|
| 那次事故的原始那一行 | ✅ 抓到 1 处 |

⇒ 以后**五条自检变六条**，第 6 条就是它。
